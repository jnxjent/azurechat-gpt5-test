# Canvasの会社資料をAccount選択へ接続

## 現象と変更

「J＆T環境の初回訪問用の資料をCanvasで作って」が旧Contact検索へ入り、003系IDの連絡先を会社資料の根拠として返した。前回の所有者項目検証の修正だけでは、この入口の誤振り分けは直らなかった。ログアウトでは解決しない。

- WebはCanvasの出力指定を `presentation=canvas` として署名対象のリクエストに明示する。会社名・所有者・日付・集計はキーワード正規表現で決めず、strict schemaの構造化解析で決める。
- Canvas資料の解析は、Account/Opportunity等の汎用レコード取得と既存の専門データ検索を分類する。会社概要・訪問資料・面談準備はAccountを主な出典とし、Contactを会社の代替にしない。日報・廃棄物・特定個人の連絡先など、明示された専門検索は既存経路を維持する。
- 会社資料は共通Account resolverで候補を提示する。複数あれば取得を中断し、サーバー保存済みの候補からユーザーに1件選ばせる。選択後はAccount IDの一致条件で取得する。モデルの推測で候補を選ばない。
- Account資料の項目はアプリ側で固定し、既存のschema/FLSチェックと本人SF認可を適用する。日付・担当範囲・集計の検証は維持。解析不能時は旧Contactへ戻らず停止する。
- 候補選択の「2番で」だけを要約AIへ渡していた箇所を修正し、サーバーで検証した元の資料作成依頼を渡す。UIも候補選択の直後に限って元のCanvas出力意図を引き継ぐ。UIの引継ぎは認可には使用しない。

## 検証

- Gateway全270件成功。会社資料の候補提示までは詳細取得をせず、選択後はAccount IDで1件に限定し、Contactを問い合わせないことをFlask routeで確認。
- Web配備用29コマンド成功、TypeScript型検査成功。実Web入口でCanvas出力属性・候補番号・元依頼の引継ぎを確認。
- 実Azureモデルで初回訪問資料・会社概要のAccount解釈、完了予定日を指定した月別商談集計のOpportunity解釈とコンパイルが成功。日付の基準がない月別集計は確認を返し、推測で決めない。
- 実際の本人OAuthによる28候補の表示と、ブラウザーでの選択後Canvasは配置後の利用者確認が必要。ローカルテスト成功だけで実ブラウザー試験完了とはしない。

本番へのpush・merge・配置・設定変更は絶対禁止。対象は `azurechat-gpt5-test` と `sf-gateway-personal-test` のみ。共有 `sf-gateway-test` は変更しない。
